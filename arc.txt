model Integration {
  id           String              @id @default(cuid())
  projectId    String
  provider     String              // 'yandex_direct', 'vk_ads', ...
  status       IntegrationStatus   @default(PENDING)
  accessToken  String?             // зашифрован
  refreshToken String?             // зашифрован
  expiresAt    DateTime?
  metadata     Json?               // настройки (счётчик, кампания и т.д.)
  lastSyncAt   DateTime?
  createdAt    DateTime            @default(now())
  updatedAt    DateTime            @updatedAt

  project      Project             @relation(fields: [projectId], references: [id], onDelete: Cascade)
  syncLogs     IntegrationSync[]

  @@unique([projectId, provider])
  @@index([projectId])
  @@map("integrations")
}

model IntegrationSync {
  id            String      @id @default(cuid())
  integrationId String
  status        String      // 'success', 'error'
  recordsCount  Int         @default(0)
  error         String?
  startedAt     DateTime    @default(now())
  finishedAt    DateTime?

  integration   Integration @relation(fields: [integrationId], references: [id], onDelete: Cascade)

  @@index([integrationId, startedAt])

🔐 Безопасность при работе с чувствительными данными
Что мы должны сделать обязательно
1. Шифрование токенов в БД
Access и refresh токены — нельзя хранить в открытом виде.
Решение: AES-256-GCM с ключом из env.

ts
// infra/crypto/crypto.service.ts
import { createCipheriv, createDecipheriv, randomBytes } from 'crypto';

@Injectable()
export class CryptoService {
  private readonly key: Buffer;

  constructor() {
    this.key = Buffer.from(process.env.ENCRYPTION_KEY!, 'hex');
  }

  encrypt(plaintext: string): string {
    const iv = randomBytes(12);
    const cipher = createCipheriv('aes-256-gcm', this.key, iv);
    const encrypted = Buffer.concat([
      cipher.update(plaintext, 'utf8'),
      cipher.final(),
    ]);
    const authTag = cipher.getAuthTag();
    return `${iv.toString('hex')}:${authTag.toString('hex')}:${encrypted.toString('hex')}`;
  }

  decrypt(ciphertext: string): string {
    const [ivHex, authTagHex, dataHex] = ciphertext.split(':');
    const decipher = createDecipheriv(
      'aes-256-gcm',
      this.key,
      Buffer.from(ivHex, 'hex'),
    );
    decipher.setAuthTag(Buffer.from(authTagHex, 'hex'));
    const decrypted = Buffer.concat([
      decipher.update(Buffer.from(dataHex, 'hex')),
      decipher.final(),
    ]);
    return decrypted.toString('utf8');
  }
}

2. OAuth state (CSRF-защита)
Каждый OAuth-запрос должен иметь уникальный state, который проверяется на callback.

ts
const state = randomBytes(32).toString('hex');
// сохраняем в Redis с TTL 10 минут

3. Проверка tenant isolation
Интеграция всегда привязана к projectId.
Перед любым действием — проверка через MembershipService.

4. Rate limiting для внешних API
Каждый провайдер имеет лимиты запросов.
Используем очередь (BullMQ) + retry с backoff.

5. Аудит всех действий
Каждый факт подключения, синхронизации, отключения — в ActivityLog.

6. Ротация ключей
Раз в N месяцев — ротация ENCRYPTION_KEY с перешифровкой всех токенов.

7. Минимальные scope'ы
При OAuth запрашиваем только нужные права, не больше.

🎯 Мультифакторный канбан
Ты сказала «мультифакторовая» — это ключевое!
Канбан должен поддерживать:

1. Разные workflow для разных проектов
SEO-проект: Audit → Fix → Verify → Done

Разработка: Backlog → Dev → QA → Prod

Маркетинг: Idea → Draft → Review → Published

Продажи: Lead → MQL → SQL → Deal

Один движок — разные процессы.

2. Разные сущности на одной доске
Канбан может показывать разные типы карточек:

🟦 Задачи

🟩 Баги

🟨 Идеи

🟥 Инциденты

Каждый тип — свой Entity, но на одной доске.

3. Фильтры и группировки
По исполнителю

По приоритету

По дедлайну

По тегам

По кастомным полям

4. Разные представления
Канбан (по статусам)

Список (таблица)

Календарь (по датам)

Timeline (Gantt)

Дашборд (виджеты)

Всё это — одни и те же Record, разные View.

Модель
prisma
model View {
  id        String    @id @default(cuid())
  projectId String
  entityId  String
  name      String
  type      ViewType  @default(KANBAN)
  config    Json      @default("{}")
  
  // config:
  // {
  //   "groupBy": "status",
  //   "filters": [...],
  //   "sort": [...],
  //   "columns": [...],
  //   "cardFields": [...]
  // }
  
  project   Project   @relation(...)
  entity    Entity    @relation(...)
  
  @@index([projectId])
  @@map("views")
}

enum ViewType {
  TABLE
  KANBAN
  CALENDAR
  TIMELINE
  DASHBOARD
}
🎯 Что даёт мультифакторность
Сценарий 1: SEO-агентство
Доска «SEO-задачи»

Workflow: Detected → Analyzing → In Progress → Review → Resolved

Поля: URL, Severity, Type, Assignee

Группировка: по Severity

Доска «Контент»

Workflow: Idea → Draft → Review → Published

Поля: Title, Keywords, Author, PublishDate

Группировка: по Author

Сценарий 2: Разработка
Доска «Спринт»

Workflow: Backlog → To Do → In Progress → Review → Done

Поля: Story Points, Assignee, Priority

Группировка: по Assignee

Доска «Баги»

Workflow: New → Triaged → Fixing → Testing → Closed

Поля: Severity, Affected, Environment

Группировка: по Severity

Сценарий 3: Маркетинг
Доска «Кампании»

Workflow: Idea → Planning → Active → Paused → Completed

Поля: Budget, Channel, CTR, ROI

Группировка: по Channel

📌 Что делаем
Канбан — отдельный большой модуль, который появится на фазе 4 roadmap.

Но у нас уже готов фундамент:

✅ Workflow + Step + Transition

✅ Record.data (JSONB)

✅ Entity + Field

✅ ProjectModule

Осталось:

⬜ View (модель + API + UI)

⬜ DnD-интерфейс на фронте

⬜ Real-time обновления через WebSocket
